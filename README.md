# Agent 与 Skill 提示词仓库

这个仓库用于集中管理可复用的 Agent 与 Skill 提示词，目标是把“项目理解”“结构沉淀”“上下文记忆”拆成清晰、可组合的能力模块，方便在不同项目中复用。

## Agent

### ContextReader

位置：Agent/ContextReader.md

职责：
- 扫描代码仓库，提取技术栈、目录结构、架构分层与当前开发状态。
- 通过提问补齐上下文中无法直接从代码验证的信息。
- 产出结构化项目总结，供后续 Skill 写入项目记忆或结构文档。

边界：
- 只负责读取、分析、总结。
- 不负责编写业务代码。
- 不应凭空推断技术栈或架构，缺失信息需要向用户确认。

适用场景：
- 接手一个新仓库时快速完成项目扫描。
- 在正式编码前，为 AI 建立统一的项目认知。
- 为后续记忆沉淀提供高质量输入。

### TestAnalyzer

位置：Agent/TestAnalyzer.md

职责：
- 基于静态阅读分析现有测试框架、测试覆盖面和潜在高风险路径。
- 输出测试策略、测试缺口和优先补充的测试点。
- 在获得用户明确同意后，执行最小范围的验证命令。
- 在需要时允许于 `test/` 目录下生成测试用例。

边界：
- 默认先做静态测试分析，不直接运行命令。
- 任何执行动作都必须先说明命令、范围、目的和风险，并征得用户同意。
- 不应默认修改业务代码。
- 新增测试应优先遵循仓库已有测试框架和目录约定。

适用场景：
- 评估某个模块是否缺少关键测试。
- 在修复缺陷前先补测试，降低回归风险。
- 对执行测试命令保持审慎和可控。

### RequirementAnalyst

位置：Agent/RequirementAnalyst.md

职责：
- 与用户对话，澄清并补全模糊需求。
- 将目标、范围、约束、验收条件整理为可执行开发文档。
- 默认将开发文档输出到 `docs/`，也支持用户指定其他路径。

边界：
- 重点是需求澄清和文档产出，不直接进入编码实现。
- 对未确认信息要标记为假设或待确认问题，不能自行脑补。
- 在需求不完整时应继续提问，而不是直接生成看似完整但不可靠的方案。

适用场景：
- 用户只有粗略想法，需要整理成开发说明。
- 编码前先形成明确范围和验收标准。
- 为后续实现 Agent 提供稳定输入文档。

## Skills

### commit-structure

位置：Skills/commit-structure.md

职责：
- 接收来自 ContextReader 的结构化项目上下文。
- 将项目蓝图与 AI 编码约定固化到 `.github/projectStructure/`。

输出内容：
- `.github/projectStructure/blueprint.md`
- `.github/projectStructure/ai_conventions.md`

适用场景：
- 初始化项目结构档案。
- 项目发生较大重构后，更新长期有效的架构描述。
- 固化仓库级 AI 协作约束。

### memory

位置：Skills/memory.md

职责：
- 管理项目级动态记忆，沉淀当前进度、阻塞项、下一步动作与 AI 协作约定。
- 按内容类型将信息写入 `.github/memory/`。

核心文件：
- `.github/memory/project_intro.md`：项目介绍、技术栈、总体架构。
- `.github/memory/context_memory.md`：当前进展、待办、风险、近期决策。
- `.github/memory/ai_conventions.md`：仓库内 AI 的编码与协作规则。

适用场景：
- 在会话结束前保存当前开发上下文。
- 为跨设备、跨会话协作保留连续性。
- 维护项目运行中的动态状态，而不是静态结构。

## 推荐使用方式

### 场景 1：初始化一个新项目的 AI 上下文

1. 先使用 ContextReader 扫描项目。
2. 由用户确认扫描结果是否准确。
3. 将长期稳定的信息交给 commit-structure 固化。
4. 将当前阶段进展和约束交给 memory 写入动态记忆。

### 场景 2：继续一个已经在开发中的项目

1. 先读取 `.github/memory/` 中已有内容。
2. 用 ContextReader 补充扫描最近变化。
3. 使用 memory 更新当前状态、待办和约定。
4. 若架构发生明显变化，再调用 commit-structure 更新结构文档。

### 场景 3：先做测试分析再决定是否执行

1. 使用 TestAnalyzer 读取现有代码与测试目录。
2. 先输出测试缺口、风险点和建议新增的测试例。
3. 若需要运行验证命令，由用户显式批准。
4. 如需补测试，可在 `test/` 下生成对应测试文件。

### 场景 4：先梳理需求再进入开发

1. 使用 RequirementAnalyst 与用户对齐目标、范围和约束。
2. 将结果整理为开发文档。
3. 默认写入 `docs/`，或按用户要求写入指定路径。
4. 文档确认后再交给实现 Agent 开始开发。

## 模块分工

可以把这些模块理解为几类协作职责：

- ContextReader：负责“读懂项目”。
- TestAnalyzer：负责“分析测试与验证风险”。
- RequirementAnalyst：负责“把需求整理成开发文档”。
- commit-structure：负责“沉淀稳定结构”。
- memory：负责“维护动态上下文”。

这种拆分的好处是：
- 避免把一次性对话内容混进长期结构文档。
- 避免项目蓝图被临时任务信息污染。
- 让 Agent 与 Skill 的职责边界更清楚，便于后续扩展更多模块。
